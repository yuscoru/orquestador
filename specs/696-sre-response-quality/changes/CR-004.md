# CR-004 — Make Quality point status forward-compatible and visibly degraded

status: IMPLEMENTED — BROWSER EVIDENCE PENDING
origin: ISS-007
requested: 2026-10-22 from observed concurrent evaluation results

## Motive

Agentics legitimately persists scored v4/offline-log points whose monitoring status is `judge_unavailable` when a judge score is unavailable; checkpoint remains uncommitted. The scored-point predicate introduced by CR-001 admits those documents. The approved API response enum still allows only five non-null statuses, so R1/R2/R3/R6 raise HTTP 500 while serializing them. Two real runs reproduced this. The frontend would not crash on the JSON but its manual union is stale and its chart marker does not explicitly distinguish the degraded state.

## Delta

### D1 — Replace the closed enum with a forward-compatible status string

Previous: `QualityEvaluationPoint.status` is a closed five-value enum or `null`; any new writer string
causes response validation to fail for the complete list/detail.

New: `status: string | null` with no OpenAPI enum. Document current known values (`measured`,
`low_sample`, `no_activity`, `no_eligible_cases`, `evidence_incomplete`, `judge_unavailable`) but
preserve every future non-null writer string literally. `null` remains exclusively missing/legacy
monitoring status. Unknown strings never cause R1/R2/R3/R6 to fail and are never coerced to measured,
null or another known value.

If the persisted field exists and is non-null but is not a string, it is corrupt metadata: return the
fixed API-generated sentinel `invalid_status`, emit a structured type-only warning, and never log or
serialize the raw value. The sentinel is not a writer status and is distinct from legacy null.

### D2 — Preserve legitimate scored points across Quality routes

R1, R2, R3 and R6 return HTTP 200 and preserve `status: "judge_unavailable"` or any future writer
string when a document otherwise satisfies the CR-001 scored-point predicate. Malformed non-string
status yields `invalid_status` without dropping the point. The point is not excluded and persisted
data is not rewritten. R4 cases and static R5 are unchanged.

Both metric DTOs retain their existing semantics: numeric values remain numeric even if other judge evidence was unavailable; `value:null` remains an explicit gap and is never converted to zero. `sample_sufficient` is preserved. The API exposes neither checkpoint nor promotion inference through this point shape.

### D3 — Render known and unknown states safely

Frontend changes its status type to `string | null` and classifies values with a default branch:

- `measured`: normal/default presentation;
- `null`: “unknown (legacy)” only;
- `judge_unavailable`: known degraded/not fully evaluable;
- `invalid_status`: invalid persisted status, degraded and distinct from legacy;
- any other non-null string, including future writer values: visible generic unknown/degraded state.

No unknown/sentinel value is measured/default-green, legacy or zero. Catalog, table, tooltip and chart
use accessible degraded text/badges/markers plus a note/legend. Numeric scores remain visible when
served; null metrics remain absence/gaps. The drawer, queries, RBAC and endpoints do not change.

### D4 — Contract and regression coverage

API tests start red and prove OpenAPI nullable unrestricted string/no enum; exact preservation of all
known and future string statuses; legacy null; safe `invalid_status` mapping plus type-only logging for
bool/number/object/array; and HTTP 200 through R1/R2/R3/R6 using synthetic scored fixtures. Totals,
latest and metrics remain unchanged; R4/R5 remain green; raw malformed values never appear in
response/log. Frontend has no persistent test framework: validate typed build/lint and the existing
temporary browser interception/evidence harness for known degraded, future unknown, invalid sentinel,
null unavailable and legacy points at desktop/narrow viewport. Introducing a test framework is out of scope.

## Contracts affected

- C-01 `quality-read-api`: `QualityEvaluationPoint.status` changes from a closed nullable enum to a
  nullable open string with documented known values and reserved `invalid_status`; R1/R2/R3/R6 use it.
- C-03 writer schema is not changed; this delta makes the consumer compatible with its observed output.
- C-02 authorization is unchanged.

Compatibility: existing JSON values are unchanged, but OpenAPI changes from enum-or-null to
string-or-null. Generated/exhaustive clients must replace exhaustive enum handling with known branches
plus a default. The manual frontend type must update. `cassdk` remains unresolved and must adopt the
open-string/default-branch contract in future client work.

## Consistency analysis

`/speckit.analyze` is unavailable in this orchestration repository. Manual analysis completed across `spec.md`, `plan.md`, `contracts.md`, `spec-frontend.md`, `plan-frontend.md`, `tasks.md`, API commit `f34bf9c`, frontend commit `0032c68`, and Agentics commit `5e720a3`:

- CR-001 intentionally removed status from the valid-point predicate, so exclusion is not a valid remedy.
- CR-002 null means missing legacy monitoring only; neither known/future strings nor malformed
  non-string metadata map to null. `invalid_status` preserves availability without legacy conflation.
- Numeric metric and unavailable semantics remain unchanged.
- The API routes share one DTO; all four affected surfaces need regression coverage.
- Frontend runtime is tolerant but type and visual semantics are incomplete; no page/query change is necessary.
- No Agentics, persistence, RBAC, credential, evaluation or checkpoint behavior changes.
