# ISS-001 — History endpoint filters out historical evaluations of a target

status: TRIAGED
reported: 2026-10-19 by user (admiral session)
repository: soarplus-api
touches_contract_or_spec: yes
triage: done (2026-10-19, api analyst, 696-api-11)

## Observation

The query behind the per-target evaluations endpoint
(`GET /quality/targets/{target_type}/{target}/evaluations`, plan.md §3 R2) applies a filter
(the valid-point predicate, plan.md §3 "Valid-point predicate") that, after user review and
analysis, should not apply to the history: the endpoint should return the metric results of
**all** historical evaluations of the target, not only those matching the predicate.

Expected (user): all historical evaluations of a target, with their metrics, are listed.
Observed (per approved design): only documents satisfying the valid-point predicate
(`checkpoint_committed`, one of five contract statuses, no rescore/validation markers) qualify;
the rest are invisible.

## Triage

outcome: SPEC_CHANGE
evidence: >
  api analyst, ANSWER 696-api-11 on HEAD d8faac3 (quality files clean, read via git show).
  Predicate QUALITY_VALID_POINT_FILTER defined once in api/AWS/documentdb.py:41-48 and applied by
  all four queries (history 1125/1146, catalog 1153, detail 1164, cases 1170), matching plan.md §3
  exactly. Excluded from history: non-v4/non-offline_log docs, checkpoint_committed!=true, status
  outside the five contract statuses (judge_unavailable never shows, spec C3), rescored docs,
  validation runs. The 404 of R2 also depends on the predicate. Implementation conforms to the
  Gate-2 design, so not an implementation defect; showing all history is a contract/design change.
  Technical note: relaxing the predicate only in R2 breaks total==sum coherence and the
  single-predicate invariant; the CR must decide which conditions remain (schema_version/mode
  almost certainly stay).
