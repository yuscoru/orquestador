# Workflow State Protocol

## Purpose

This protocol defines **where orchestration state lives on disk** and **who owns
each file**.

Chat context is lost when a session ends. Without a fixed layout, every session
invents its own and traceability is lost.

The rule is simple:

```text
If it must survive the session, it is a file in this repository.
```

---

# Scope boundary

This repository stores **orchestration** state: planning, assignment, routing
and results.

It does **not** store repository implementation state.

```text
soarplus-dev-orchestration     what was planned, assigned, answered, routed
<product repository>           what was actually implemented
```

Implementation reality remains owned by the product repository, in its own
`specs/<feature>/tasks.md` and `IMPLEMENTATION-CHECKPOINT.md`.

Orchestration artifacts **reference** those files. They never copy their
content.

Duplicating a checkpoint here creates a second source of truth that will drift
within days. When orchestration state and a product repository disagree, the
product repository is right about implementation and this repository is right
about assignment.

---

# Layout

Spec Kit is installed in this repository. Its feature directory is reused as the
single home for everything about a feature, so there is one directory per
feature rather than two competing ones.

```text
protocols/                       orchestration contracts, feature-independent
specs/<ADO-US>-<slug>/           all state for one feature
```

The directory name uses the canonical feature identity defined in
`feature-branching.md`:

```text
specs/696-sre-response-quality/
```

There is no index file. The directory listing is the index. A maintained list
of features would be a second source of truth.

## Feature directory

```text
specs/<ADO-US>-<slug>/
    spec.md                 captain    GLOBAL spec, generated by /speckit.specify
    plan.md                 captain    GLOBAL plan, generated by /speckit.plan
    tasks.md                captain    GLOBAL tasks, generated by /speckit.tasks
    contracts.md            captain    contract registry (references, not copies)
    handoff.md              captain    implementation-ready decomposition
    WORKFLOW-STATE.md       admiral    current execution reality
    log.md                  admiral    append-only chronological record
    envelopes/              admiral    issued Task Envelopes
    results/                admiral    received Task Results and Blocker Results
```

`spec.md`, `plan.md` and `tasks.md` here are **global**: they describe the
feature across repositories. They are not the same documents as a product
repository's `specs/<feature>/spec.md`, which describes only that repository's
work.

Not every file must exist from the start. Create each when it has content.

A feature directory containing only `spec.md` is a feature in `PLANNING`. That
is valid state, not an incomplete directory.

## Task numbering

The global `tasks.md` is the **single numbering authority** for the feature.

Each task is tagged with the worker that will execute it. A product
repository's `tasks.md` is a filtered projection of the global one that
**preserves the original task ids**.

If `T014` and `T015` are assigned to `api-engineer`, the `tasks.md` in
`soarplus-api` contains `T014` and `T015`, not a renumbered `T001` and `T002`.

This keeps one identifier valid across the envelope's `spec_tasks`, the
repository's `tasks.md` and the commit trailer.

Once projected, the repository's `tasks.md` is authoritative for **progress**;
the global one remains authoritative for **scope and numbering**.

# Approval gates

Four human decision points govern a feature. The first three belong to the
`captain`, the fourth to the `admiral`.

```text
GATE 1  spec       captain    after /speckit.specify
GATE 2  plan       captain    after /speckit.plan
GATE 3  tasks      captain    after /speckit.tasks, before handoff.md
GATE 4  delivery   admiral    before push, PR or deploy
```

All gates live in this repository. Product repositories have none; their
engineers run only `/speckit.implement`, which has no native gate.

An approval recorded only in chat did not happen. Gates 1 to 3 are recorded in
the artifact they approve:

```markdown
> Gate: approved by user on 2026-10-14.
```

Gate 4 is recorded in `WORKFLOW-STATE.md` under
`delivery_authorizations_granted`.

An artifact without its gate record is a **draft**. The `admiral` MUST NOT
issue envelopes from a draft.

Gates cannot be executed inside a subagent: a subagent runs to completion and
the user cannot reply to it mid-run. Gated stages are user-driven sessions.

# Materialization

`/speckit.implement` runs `check-prerequisites.sh --require-tasks`, which
**aborts unless `plan.md` and `tasks.md` exist in the repository where it
runs**. It cannot read them from another path.

Global artifacts in this repository therefore do not satisfy it. Each product
repository needs its own feature directory before implementation can start.

## Who materializes

The repository's `-engineer`, under a Task Envelope, as its first action for the
feature.

Not the `captain`: writing into a product repository would break its write
scope, which is the central invariant of this system.

Not the `admiral`: it issues envelopes, it does not write product repositories.

## Creating is not planning

The most common misreading of this protocol is to assume that creating the
branch and the `specs/` directory requires `/speckit.specify`. It does not.

These are separable operations:

| Operation | Mechanism | Planning? |
|---|---|---|
| create the branch | `/speckit.git.feature`, or plain `git checkout -b` | no |
| create `specs/<feature>/` and its files | `mkdir` and write | no |
| bind the active feature | `.specify/feature.json` | no |
| draft a spec from a description | `/speckit.specify` | **yes** |
| derive a plan from the spec | `/speckit.plan` | **yes** |
| derive tasks from the plan | `/speckit.tasks` | **yes** |
| execute the tasks | `/speckit.implement` | no, execution |

The engineer performs the first three and the last. Never the three marked as
planning.

`/speckit.git.feature` exists precisely for this: its own documentation states
it "handles branch creation only — the spec directory and files are created by
the core `/speckit.specify` workflow". Used standalone, with `GIT_BRANCH_NAME`
exported, it creates the correctly named branch and nothing else.

`/speckit.implement` does not know or care how the files arrived. It runs
`check-prerequisites.sh --require-tasks`, which only checks that `plan.md` and
`tasks.md` **exist** in the resolved feature directory. Files written by
projection satisfy it exactly as generated ones would.

## Binding the active feature

`get_feature_paths` resolves the feature directory in this order:

```text
1. SPECIFY_FEATURE_DIRECTORY   environment variable, current shell only
2. .specify/feature.json       committed file, survives the session
3. branch-name prefix lookup   legacy fallback, breaks the convention
```

The environment variable dies with the shell. During materialization the
engineer MUST also write:

```json
{"feature_directory": "specs/<ADO-US>-<slug>"}
```

to `.specify/feature.json`, which is a tracked file in these repositories. That
is what makes the binding durable across sessions.

Confirm the repository's own conventions before committing it; it changes the
active feature for everyone working in that repository.

## What is produced

In the product repository, at `specs/<ADO-US>-<slug>/`:

| File | Origin |
|---|---|
| `spec.md` | projection of the global `spec.md`, narrowed to this repository |
| `plan.md` | projection of this repository's section of the global `plan.md` |
| `tasks.md` | filtered projection of the global `tasks.md`, ids preserved |

**All three are projections. None is regenerated.**

The repository worker does **not** run `/speckit.specify`, `/speckit.plan` or
`/speckit.tasks`. Those commands would start a second planning cycle with its
own numbering, and cross-repository traceability would be lost.

There is exactly one `specify`, one `plan` and one `tasks` per feature — in this
repository, by the `captain` — and one `implement` per product repository.

```text
1 specify  +  1 plan  +  1 tasks   global, orchestration
N implement                        one per product repository
```

Task ids are the thread: the same `T014` appears in the global `tasks.md`, in
`spec_tasks` of the envelope, in the repository's `tasks.md` and in the commit
trailer. Renumbering anywhere cuts the thread.

## Where repository depth comes from

The global `plan.md` carries a per-repository section detailing approach,
constraints, contracts and validation expectations. That section is what gets
projected.

Its technical depth comes from the `-analyst` workers in `ANALYZE` mode. That is
why analysts exist: so the `captain` can plan with repository evidence without
either guessing or writing in the repository.

Implementation detail discovered **during** implementation does not go back into
`plan.md`. It goes into the repository's `IMPLEMENTATION-CHECKPOINT.md`, which
every product repository already defines as its current-reality artifact.

If the planned approach turns out to be unworkable, that is a blocker for the
`captain`, not a local rewrite.

## Sequence

```text
Task Envelope received
      |
      v
export GIT_BRANCH_NAME="<repository.branch>"
export SPECIFY_FEATURE_DIRECTORY="specs/<ADO-US>-<slug>"
      |
      v
create or switch to the feature branch
      |   /speckit.git.feature, or git checkout -b
      v
mkdir -p specs/<ADO-US>-<slug>/
      |
      v
write .specify/feature.json -> {"feature_directory": "specs/<ADO-US>-<slug>"}
      |
      v
project spec.md, plan.md, tasks.md from the global artifacts
      |
      v
/speckit.implement      prerequisites now satisfied
```

No planning command appears in this sequence. The branch, the directory and the
three files are created by ordinary operations; only the final step is a Spec
Kit command, and it is execution, not planning.

Materialization happens **once per feature per repository**. A later envelope
for the same feature finds the directory already present and skips to
implementation.

## Divergence rule

After materialization the two levels serve different questions:

```text
global  specs/<feature>/     what the feature must achieve, who owns what
local   specs/<feature>/     what this repository implements, and its progress
```

When they disagree about **scope**, the global artifact is right and the
divergence is a blocker, not a local correction.

When they disagree about **progress or implementation detail**, the repository
is right.

An engineer that discovers the global scope is wrong returns a blocker. It does
not silently widen its local `spec.md`.

# File ownership

Two roles write to this repository. Ownership prevents collision.

| Path | Writer | Readers |
|---|---|---|
| `protocols/**` | human | everyone |
| `.specify/**` | human | everyone |
| `specs/*/spec.md` | `captain` | everyone |
| `specs/*/plan.md` | `captain` | everyone |
| `specs/*/tasks.md` | `captain` | everyone |
| `specs/*/contracts.md` | `captain` | everyone |
| `specs/*/handoff.md` | `captain` | `admiral` |
| `specs/*/WORKFLOW-STATE.md` | `admiral` | everyone |
| `specs/*/log.md` | `admiral` | everyone |
| `specs/*/envelopes/**` | `admiral` | everyone |
| `specs/*/results/**` | `admiral` | everyone |

The `captain` MUST NOT write execution state.

The `admiral` MUST NOT rewrite planning artifacts. When a plan is wrong, the
`admiral` routes the correction back to the `captain` rather than editing
`plan.md` directly.

Repository workers never write here. They write to their own repository and
return a protocol response; the `admiral` persists it.

# `WORKFLOW-STATE.md`

The single answer to "where is this feature right now".

Mutable. Overwritten as reality changes. Must be readable in under a minute.

```yaml
feature:
  ado_user_story: 696
  slug: sre-response-quality

phase: IMPLEMENTING

updated: 2026-10-14

repositories:
  - name: soarplus-agentics
    worker: agentics-engineer
    branch: feature/696-sre-response-quality
    status: IMPLEMENTING
    last_result: results/2026-10-13-agentics-engineer-934.md
    implementation_reality: >
      specs/696-sre-response-quality/IMPLEMENTATION-CHECKPOINT.md

active_blockers:
  - results/2026-10-13-api-engineer-941-blocker.md

pending_next_actions:
  - Await CAS account, capability and Secret provisioning.

delivery_authorizations_granted:
  create_pr: false
  deploy: false
```

Rules:

- `phase` uses the orchestration state model defined in the `admiral` agent;
- every repository listed MUST name a registered worker;
- `implementation_reality` is a **path reference** into the product repository,
  never a copy of its content;
- a blocker stays listed until a result supersedes it;
- `updated` is the date of the last real change, not of the last read.

# `log.md`

Append-only. Never edited, never reordered, never pruned.

One entry per orchestration event:

```markdown
## 2026-10-13 — envelope issued

worker: api-engineer
task: 941
envelope: envelopes/941-api-engineer.md
reason: Captain handoff repositories[1]

## 2026-10-13 — blocker received

worker: api-engineer
type: CONTRACT_CHANGE_REQUIRED
result: results/2026-10-13-api-engineer-941-blocker.md
routed_to: captain
```

`WORKFLOW-STATE.md` says where you are. `log.md` says how you got there.

When they disagree, `log.md` is the evidence and `WORKFLOW-STATE.md` is the
defect.

---

# `envelopes/`

One file per issued Task Envelope, containing the exact payload sent.

```text
envelopes/<ado-task>-<worker>.md
envelopes/941-api-engineer.md
```

A re-issued envelope after a resolved blocker appends a sequence suffix:

```text
envelopes/941-api-engineer-2.md
```

Never edit an issued envelope. An envelope is a record of what was actually
sent. Correcting it retroactively destroys the ability to explain a result.

---

# `results/`

One file per received Task Result or Blocker Result, containing the exact
payload returned.

```text
results/<date>-<worker>-<ado-task>.md
results/<date>-<worker>-<ado-task>-blocker.md
```

Received payloads are immutable. The `admiral` records them as returned,
including claims it intends to challenge.

If a claim is later disproved, that correction is a new `log.md` entry, not an
edit to the stored result.

---

# Persistence timing

Persist as events happen, not at the end of a session.

```text
envelope issued      -> write envelope file + log entry
result received      -> write result file + log entry + update WORKFLOW-STATE
blocker routed       -> log entry + update WORKFLOW-STATE
authorization given  -> update WORKFLOW-STATE
```

A session that persists only on completion loses everything when it is
interrupted. Interruption is the normal case in this environment, not the
exception.

---

# Resumption test

The layout satisfies its purpose when a new session, with no chat history, can
answer all of these from files alone:

1. What is this feature supposed to do? → `spec.md`
2. How was it decomposed and why? → `plan.md`, `contracts.md`
3. What was assigned, to whom? → `tasks.md`, `handoff.md`, `envelopes/`
4. What came back? → `results/`
5. Where are we now? → `WORKFLOW-STATE.md`
6. How did we get here? → `log.md`
7. What is actually implemented? → the product repository checkpoint it
   references

If any answer requires chat history, the state is incomplete.

---

# Version control

This repository is the durable layer. Durability requires version control.

Orchestration artifacts MUST be committed. An uncommitted
`WORKFLOW-STATE.md` in a container that can be recreated is not durable state.

Secrets are never written here. These files are committed and shared; the
security rules in the worker and orchestration agents apply to every artifact
in this repository.
